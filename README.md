# OIR Viewer

オリンパス `.oir` の顕微鏡画像スタック（および `.oib` / `.oif` / `.tif` / `.nd2` /
`.lif` / `.czi`）を開くビューアです。マルチチャンネルの Z スタックを手早く見て、
そのまま図に使える画像を書き出すことを目的に作っています。

- **2D** — チャンネルごとの LUT とコントラスト。カーソル位置の画素座標と、
  表示中の全チャンネルの生強度を同時に表示します。
- **Z** — 左端の縦スライダー（上が最初のスライス）、矢印キー、MIP。
- **Split** — チャンネルごとに 1 パネル＋マージ。
- **Compare** — 複数ファイルを並べて表示。パン・ズームは全同期／パネル個別を
  切り替え可能。Z と MIP の選択は共有され、ファイルごとの深さに合わせて
  クランプされます。ドラッグで並べ替えできます。
- **3D** — レイマーチングによるボリューム表示。角度を数値入力でき、表示する
  Z 範囲を指定でき、XY / YZ / XZ 面のプリセット、そして「表示中の条件で保存」
  で PNG / TIFF に書き出せます（MERGE とチャンネル別の両方）。Z スタックは最初から
  3D / Quality `Maximum`、Z が 1 枚だけの画像は 2D で開きます。3D の 100% は
  操作パネルを除いた画面にボリューム全体が収まる拡大率で、数値を直接入力できます。
- **書き出し** — チャンネル別・マージの TIFF / PNG / JPEG、Z 投影の OME-TIFF、
  ROI のラインプロファイルと面積計測。
- **Plate** — オリンパス MATL 撮影のフォルダを読み、`matl.omp2info` から
  プレート形状（未取得ウェルも含む）とウェルごとの Stitch 済みファイルを
  一覧し、ウェルを選んで開きます。ウェルの位置はラベルとステージ座標の独立した
  2つの情報から二重に検証します。保存は隣の **Plate Save** で行い、ウェルを 1 つずつ
  調整した状態のまま、プレートと同じ配置で 1 枚の PDF に書き出せます。ウェルごとの
  条件表の編集も Plate Save にあり、PDF の 2 ページ目になります。詳しくは下記。
- **スケールバー** — どのビューでも初期状態は画像の内側の左下に表示され、パンと
  ズームに追従します。ドラッグで好きな位置へ移動、ダブルクリックで左下に戻ります。
  長さ（または自動）・色・表示の有無は全ビュー共通の設定なので、図を揃えるときに
  1 本のバーで済みます。3D は透視投影のため中心深度で換算し、X/Y/Z の校正値が
  そろわない画像には数値のバーを出しません。ラベルは Arial です。

## プレートを 1 枚の PDF に書き出す

手順は「**読み込む → 各ウェルを調整する → 書き出す**」です。

1. **Plate** でフォルダを選び、ウェルを選んで **選択したウェルを開く**。
   ふつうのタブとして開きます。
2. 各タブを **3D** ビューで好きなように調整します。チャンネルの表示・色・Min/Max、
   角度、Z 範囲 — **ウェルごとに違っていて構いません**。角度と Z 範囲はウェルごとに
   記憶されるので、別のウェルを見てから戻っても設定は残ります。
3. **Plate Save** を開き、条件表と保存条件を編集して **3D → PDF を作成**。

**書き出しは各タブの「今の状態」をそのまま使います。** 開いていないウェルは出ません。
表示中のチャンネル（最大 4 つ）だけが描かれます。ウェルは 1 つずつ順に処理され、次を
読む前に前のウェルを解放します。

コントラストがウェルごとに自動調整されることはありません。あなたが決めた値がそのまま
焼き込まれます。

Plate Save では、全ウェルの拡大率を同じ値にそろえる設定が既定で有効です（初期値
100%、数値は変更可能）。無効にすると各タブで調整した拡大率を使います。保存画像の
スケールバーも既定で有効で、各ウェルの画像内左下へ入ります。実際に適用した拡大率と
スケールバーは条件表と footer に記録されます。

### 条件表

Plate Save ダイアログに、開いているウェル 1 行ずつの表が出ます。**Excel のように直接
入力できます。**

- **自動で埋まる列** — Well・チャンネル・Min/Max・角度・Z 範囲。各ウェルのビューアの
  設定から取ります。
- **書き換えられます** — 「CH1, CH2」を「GFP, DAPI」に直す、といった使い方を想定して
  います。**手で直した値は勝手に戻りません。**「自動列を現在の設定で更新」を押した
  ときだけ上書きされます。
- **列の追加・削除・並べ替え・列名の変更** — 「条件」「濃度」「継代数」など、実験ごとに
  必要な列を作れます。列名はクリックで変更できます。
- **図** を付けた列は、**その内容が各ウェルの画像の左上に印字されます**。既定では
  Well と条件の 2 列だけです。24 ウェルに全列を載せると読めなくなるためです。
- **表そのものは PDF の 2 ページ目**に、全ウェル・全列で入ります。図と条件が別ファイル
  になると、いずれ離ればなれになるためです。

解像度は 2 つ選べます。

| ボリューム | XY の上限 | 用途 |
|---|---|---|
| Low | 128 px | 一覧・当たりを付ける |
| Medium / High | 256 / 512 px | 通常 |
| Ultra | 1024 px | 図に使う |
| Max | 元のまま | 縮小も Z の間引きもしない |

| PDF のセル | 画素 |
|---|---|
| Draft / Normal / High / Max | 300 / 600 / 1200 / 2000 px |

セルを大きくするとページ自体が大きくなります（画像を引き伸ばしません。細かくならない
上にファイルだけ肥大するためです）。

**実際の上限は GPU の `MAX_3D_TEXTURE_SIZE`**で、機種によって2048だったり16384
だったりします。選んだ解像度が上限を超える場合は、読み込み前にそのGPUで扱える値へ
自動的に下げます。結果画面とPDFのfooterには、実際に使った値とGPU上限による制限を明記
します。たとえば2911×2923の実データで上限が2048なら、Maxを選んでも2048で処理され、
Ultraを選べば1024のままです。表示と異なる解像度を黙って記録することはありません。

1 つでも読めないウェルがあれば、**PDF を作らずに中止します**。取得済みのウェルが空欄で
出た PDF は、未取得だったのか失敗したのか後から見分けられないためです。

## 保存するとき

**名前を付けて保存が既定です。** 書き出し・PDF いずれもファイル名の欄があり、開いている
画像の名前が最初から入っていて、そのまま書き換えられます。

チャンネル名や Z/T の番号は自動で付きます（`名前_GFP_Z003.tif` のように）。1枚の画像に
つき何十ファイルにもなるので、入力するのは共通部分だけです。複数画像をまとめて保存する
ときは各画像が元の名前を保ち、画像ごとのサブフォルダに入ります。

**同じ名前のファイルがあると、書き込む前に止まって確認します。** 上書きされるファイル名が
一覧で出て、キャンセルすればフォルダは一切変わりません。Plate PDFは名前を入力した時点で
調べ、作成ボタンでもウェルを読み込む前に再確認するため、長い描画の後で同名に気づくことは
ありません。Z投影も同じ方式で、指定した名前のOME-TIFFだけを作ります。

開いている元画像そのものを保存先にはできません。別名のハードリンクやシンボリックリンクで
同じファイルを指している場合も、上書き確認の選択にかかわらず拒否します。表示用のRGB画像で
元の顕微鏡データを置き換える事故を防ぐためです。

以前は同名を見つけると黙って `_01` `_02` と連番を付けていました。何も失われませんが、
自分が付けていない名前で似たファイルが増え、後から区別できなくなるため、やめました。

長い書き出しの途中で元画像や保存先のファイルが変わった場合も、そのまま続けずに停止します。
確認したものとは別の内容を上書きしたり、読込前半と後半が異なる画像から図を作ったりしない
ためです。

2D画像、3D画像、Z投影、Plate PDFはいずれも、保存中の処理名と進行率をスケールで表示します。
割合はタイマーではなく、ファイル作成やウェル描画など**実際に完了した単位**から計算します。
100%になるのは、作成物を再度開いて検証し、指定先へatomicに公開できた後だけです。3D画像の
保存中は、別タブや表示モードへの移動、ファイルを開く・閉じる操作、別の保存を一時的に停止
し、途中で別の表示状態が混ざらないようにします。

使えない文字（`\ / : * ? " < > |`、末尾の「.」や空白、`CON` `NUL` などの予約名）は
入力の時点で知らせます。書き出しが終わってから失敗するのを避けるためです。

## アップデート通知

起動時に GitHub の Releases を1回だけ確認し、新しいバージョンがあれば画面上部に
知らせます。**これがこのアプリで唯一の外部通信**です。送信するのは使用中の
バージョン番号だけで、画像・ファイル名・パスは一切送りません。

確認できないとき（オフライン、プロキシ、GitHub 側の障害）は**何も表示せず黙って
続行**します。結果は6時間キャッシュされます。通知は「×」で消せ、そのバージョンに
ついては二度と出ません。

通信させたくない場合は、`backend/main.py` の `update_check` が使う
`RELEASES_API` への接続をファイアウォールで塞いでください。動作に影響はありません。

## 不具合が起きたとき

バックエンドの出力は起動ごとに `~/.oir-viewer/logs/backend-<日時>.log` に保存され
ます（Windows なら `C:\\Users\\<ユーザー名>\\.oir-viewer\\logs\\`）。直近10件が残ります。
メニューの **ヘルプ → ログフォルダを開く** からも辿れます。

エラーを報告いただくときは、このログを添えていただけると原因が特定できます。

## 知っておいたほうがいい挙動

**Z が 2 枚以上ある画像は 3D、Z が 1 枚の画像は 2D で開きます。** 3D の既定画質は
`Maximum`（原寸、ただし GPU 上限まで）です。開くときのRAM警告と、RAM不足を理由にした
**2Dで開く** / **続行** の確認は完全に廃止しました。

内部の `/api/volume-plan` は残っていますが、空きRAMの可否判定には使いません。元画像の
revision、T、元と出力のshape、読み込み状態、重量処理のepochを次のvolume requestへ結び、
受信したheader・shape・byte数まで一致することを確認するための整合性契約です。別の処理や
ファイル変更で前提が変われば、古い計画のまま描画せず再計画します。これは「間違った図を
出さない」ための検証で、実行に十分なRAMがあることを保証するものではありません。

3D の保存は、現在の画像・T・Qualityに一致するボリュームがGPUで正常に描画できるまで
無効です。読込中、GPU upload error、WebGL context loss、またはMERGE/チャンネル別画像の
一部しか取得できない場合は、黒い図や部分的な図を保存せず明示的に停止します。

**コントラストは撮影時のまま開きます。** 顕微鏡が記録した表示レンジ（LUT の
shadow / highlight）をファイルから読み、データのビット深度に合わせて変換して
います。オートストレッチではなく、顕微鏡の画面で見たとおりに開くためです。
`Auto` / `Auto All` を押すとパーセンタイルによる自動コントラストに切り替わり
ます。

一度開いたファイルの表示チャンネル・色・Min/Max・Z/T・MIP は、アプリを終了しても
`~/.oir-viewer/view-settings.json` に残ります。元画像の identity と revision が一致する
場合だけ再利用するため、同じ場所のファイルが差し替わったときに古い Min/Max を黙って
適用しません。元画像そのものには書き込みません。旧版がloopback port別の
`localStorage`へ残した未検証設定は、安全のため自動移行・再適用しません。
終了直前の編集もkeepaliveと単調な書込番号で保存し、先に送られた古い設定が後から
到着して最後のMin/Maxを上書きすることを防ぎます。

2D と 3D のそれぞれに **元ファイルの設定に全て戻す** ボタンがあります。2D では上記の
表示設定と投影を、3D ではさらにカメラ・Z 範囲・Quality を、そのファイルを開いた直後の
状態へ戻し、保存済みの調整も削除します。この操作は取り消せないため確認を表示します。

ラインプロファイルと面積計測は、**通常の1断面2D表示だけ**で使えます。MIP、Z投影、Split、
3Dでは、表示中の像と単一Z断面の数値を取り違えないよう無効になります。

ただし、**LUT がビット深度の全域を占めているファイルは、定義上そのまま眠い
画像として開きます**。これは誰も LUT を触らずに撮ったときに記録される値です。
その場合は `Auto` が手っ取り早い解決です。

Min / Max のスライダーとヒストグラムは、宣言されたビット深度ではなく
**チャンネルごとの実データの尺度**に合わせて目盛りが決まります。12 bit と記録
されていても実データが 0〜600 程度なら、スライダーの大半が無効にはなりません。

**分割された `.oir` を検出します。** オリンパスは 1 GB を超えるデータセットを
`<名前>.oir` と、拡張子のない `<名前>_00001`, `_00002`, … に分割します。`.oir`
だけを開いても一見動きますが、**スタックの一部しか見えません**（例: 50 枚中
13 枚）。本ビューアはこれを検出して警告します。**Open** から元の保存場所の
ファイルを指定してください。付随ファイルが一緒に読み込まれます。ドラッグ＆
ドロップでは付随ファイルを持ち込めません。

Windows では、元画像・分割ファイル・検証後に再利用する投影 OME-TIFF の変更検出に
NTFS/ReFS の USN change journal を使います。ファイルサイズと更新時刻だけでは、
同じサイズの瞬時上書きを見逃すことがあるためです。

**exFAT / FAT でも開けます。** これらは change journal を持たないので、変更検出は
ファイルサイズ・更新時刻・作成時刻の比較になります。Mac と Windows で共有する
ドライブは exFAT にするしかないため、以前のように停止するのではなく、弱い方法で
続行します。記録には**どちらの方法で検出したかが残る**ので、NTFS で取った記録と
混同されることはありません。

弱くなる点は1つだけです。**ファイルサイズが同じままの瞬時上書きが、更新時刻の
分解能内に収まった場合**は検出できません。厳密さが要るときは change journal が
有効なローカル NTFS/ReFS に置いてください。

ドライブの切断や読み取りエラーは、従来どおり明示的に停止します（弱い検出に
落とすのは、ファイルシステムが journal を持たない場合だけです）。

## インストール

[Releases](../../releases) からお使いのプラットフォーム用のインストーラを
ダウンロードしてください。それ以外に必要なものはありません。Python と Java は
同梱されているので、別途の準備は不要です。

- macOS: `OIR Viewer-<version>-arm64.dmg`（Apple シリコン）または `-x64.dmg`（Intel）
- Windows: `OIR Viewer Setup <version>.exe`

### 初回起動時

コード署名をしていないため、OS が一度だけ「開発元が確認できない」旨の警告を
出します。想定どおりの動作で、アプリ自体の問題ではありません。

- **macOS** — ダブルクリックすると「開発元が未確認のため開けません」と出ます。
  代わりに**アプリを右クリック（または Control + クリック）→ 開く → 開く**を
  選んでください。必要なのは初回だけです。最近の macOS では、システム設定 →
  プライバシーとセキュリティ → *このまま開く* にボタンが出ることがあります。
- **Windows** — SmartScreen が「WindowsによってPCが保護されました」と表示
  します。**詳細情報 → 実行**を選んでください。

初回起動は 2 回目以降より数秒長くかかります。同梱の Java 実行環境をそのとき
初期化するためです。

## ソースから動かす

```bash
# バックエンド
python3 -m pip install -r backend/requirements.txt
python3 backend/main.py --no-webview        # 選ばれたポート番号が表示されます

# フロントエンド（別ターミナル）
cd frontend && npm install && npm run dev
```

バックエンドは空いているポート（8765 以降）を選び、`frontend/.backend-port` に
書き出します。Vite の開発用プロキシがそれを読むので、8765 が既に使われていても
設定を書き換える必要はありません。

一度ビルドしてバックエンドに配信させることもできます。配布版と同じ構成で、
プロセスもポートも 1 つ、プロキシなしです。

```bash
cd frontend && npm run build
python3 backend/main.py --no-webview        # 表示された URL を開く
```

## デスクトップアプリのビルド

`.oir` の読み込みには Java が必要（Bio-Formats）なので、JRE と Bio-Formats の
jar をビルドに同梱します。`stage_runtime.py` は通常の読み込み経路を一度実行し、
そこで解決されたものをコピーしてきます。

```bash
python3 scripts/stage_runtime.py            # → backend/runtime（約 155 MB）
(cd frontend && npm ci && npm run build)
pyinstaller backend/oir-viewer-backend.spec --noconfirm --distpath dist --workpath build
(cd desktop && npm install && npx electron-builder)
```

インストーラは `release/` に出力されます。`backend/runtime/` は生成物なので
git 管理外です。

Mac 用アプリを Windows で（またはその逆で）ビルドすることはできないため、
[`.github/workflows/build.yml`](.github/workflows/build.yml) が各プラット
フォームをそれぞれのランナーでビルドします。`v*` タグを push すると
インストーラが Release に添付されます。

## 構成

```
backend/     FastAPI: 画像を読み、スライスをバイナリで配信し、書き出しを行う
             main.py      API・静的配信・ポート選択
             reader.py    Bio-Formats / TIFF の読み込み、JVM 起動、メタデータ
             processor.py コントラスト、ヒストグラム
             roi.py       ラインプロファイル、ROI 統計
frontend/    React + Vite + Tailwind + zustand。Canvas2D、3D は three.js
desktop/     Electron シェル: バックエンドを起動し、ウィンドウを開く
scripts/     stage_runtime.py
```

アプリが書き出すデータは `~/.oir-viewer/` に置かれます（`session.json` が開いて
いたファイルを、`view-settings.json` が元画像の revision に結び付いた表示設定を記憶し、
`uploads/` にドロップされたファイルが入ります）。
